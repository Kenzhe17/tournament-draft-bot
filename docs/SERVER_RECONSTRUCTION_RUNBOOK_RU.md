# Discord Server r!z3 — применение реконструкции

Статус: код подготовлен для staging; изменения живого Discord, production-деплой и merge в эту работу не входят. Не считать полную реконструкцию завершённой до фактических Discord/PG-проверок и применения согласованной миграции.

## Реализованные элементы

- Главная карточка **Discord Server r!z3**, без рекламного описания, пять основных кнопок.
- «Играть»: активные CS/BR/Ultimatum, «Мой турнир» по Discord ID, «Организатору» с переходом в существующие панели, «Расписание» на основе настоящих Discord Scheduled Events. Пустое расписание не заполняется выдуманными турнирами. Автоматическое создание событий/напоминаний не реализовано.
- Монеты, доступный REP, SHOP 2.0, инвентарь, рейтинги, жалобы и апелляции.
- Кнопка комнаты **ID** выдаёт только идентификатор приватно с повторной проверкой участия. **Пароль публично в карточке комнаты**, согласно последнему требованию владельца. В общий чат пароль не копируется.
- Компактное welcome со ссылками «Открыть старт» и «Правила». Нет поиска welcome-канала на чужих серверах. Published welcome.card в Control Center по-прежнему может переопределить стандартный вид — проверить и привести его к новому стилю отдельно.
- Восемь разделов `/info` переписаны под турнирную модель. Ключи разделов сохранены. Старые баннеры убираются при обновлении сообщения; ошибки редактирования не создают новое сообщение.
- Подписки по форматам: отдельные permissionless-роли, не роли участников BR/Ultimatum и не роли персонала. Анонсы создания настоящего турнира используют подписку соответствующего формата. Новые анонсы используют durable pending/sent, повтор не создаёт второй пинг. Старые записи, созданные до новой версии, не мигрируются задним числом.
- Механизм структуры сервера: план, применение, статус, откат; каждое действие записывается до обращения к Discord. В архив переносится только явно выбранный список. Каналы, сообщения и роли не удаляются.

## Предварительная проверка

1. Не использовать production bot token в staging. Подготовить отдельного бота, сервер, PostgreSQL и DATA_DIR.
2. Бэкап PostgreSQL и production-volume сделать средствами действующей инфраструктуры и отдельно проверить восстановление. JSON плана — это резервная копия структуры каналов и ACL, **не бэкап PostgreSQL, сообщений Discord или всей конфигурации**.
3. У бота для миграции должно быть Manage Channels; для подписок — Manage Roles и роль выше создаваемых ролей. Владелец выполняет команды через аккаунт администратора. Служебные роли и их иерархия не переписываются автоматически.
4. Проверить источники ID (env, Control Center, info_store, server_layout). Не использовать каналы другого сервера. Устранить неоднозначные привязки до планирования.
5. Выполнить оставшиеся 136 реальных PostgreSQL-тестов, затем Discord E2E: участник/зритель/организатор/модератор, мобильный клиент, перезапуск, тайм-аут API и конкурентные нажатия.

## Структура

| Категория | Каналы |
|---|---|
| ИНФОРМАЦИЯ | 🏠・старт, 📖・информация, 📢・объявления, 🎭・роли, 👋・приветствия |
| ТУРНИРЫ | 🏆・турнир-1/2/3, 🪂・battle-royale, 📜・журнал, 🔑・данные-комнаты |
| СООБЩЕСТВО | 💬・общение, 🤖・команды-бота, 🎮・мини-игры, 📸・моменты |
| ГОЛОСОВЫЕ | существующие TempVoice/личные/командные каналы после отдельной проверки интеграции |
| КОМАНДА | скрытая категория для персонала; существующие служебные каналы не перемещаются автоматически |
| лишние-каналы | последняя категория; явно выбранные лишние каналы с сохранением их индивидуальных прав |

Существующие каналы переиспользуются по ID или однозначному имени. Отсутствующие турнирные каналы, BR, журнал и канал комнат не создаются «наугад». Старые категории не удаляются. Непривязанные каналы перечислены в `unassigned` — это инвентаризация, не доказательство ненужности.

## План и применение

Команды загружены отдельным `cogs.server_reconstruction`.

1. `/server reconstruction action:plan archive_ids:<ID1,ID2>`
2. Скачать прикреплённый JSON. Проверить `before`, `bindings`, `operations`, `busy_skipped`, `archive_selected`, `unassigned`.
3. Каналы активных турниров не переносятся. Дождаться завершения и сформировать следующий план. Не обходить эту проверку ручной правкой файлов.
4. После проверки конкретного плана: `/server reconstruction action:apply plan_id:<ID>`.
5. `/server reconstruction action:status` — состояние и журнал. При новой миграции предыдущий план сохраняется в `DATA_DIR/server_layout/history/<guild_id>/<plan_id>.json`.
6. Изменения прав/структуры после планирования отменяют применение: нужен новый план.

Миграция не запускается при старте бота. Нет cron, автоматического удаления и повторов неопределённых Discord-операций.

## Публикация интерфейсов

После успешного применения проверить сохранённые bindings и в нужном канале выполнить:

- `/server hub_publish` в 🏠・старт: существующая панель обновляется, а не дублируется.
- `/info publish` для первой публикации; `/info update` для обновления существующих карточек. Канал выбирается из сохранённой привязки миграции. Если информация уже опубликована в другом канале, переносить его с сохранением ID.
- `/server room_cards_secure` — историческое имя команды; теперь это обновление существующих карточек до текущего оформления: **пароль публичный**, кнопка ID приватная. Законченные неподдерживаемые карточки превращаются в архивные.
- `/server notification_roles` — один раз создаёт три роли подписок. Повтор использует сохранённые ID. Наличие одноимённой непривязанной роли требует ручной сверки.
- `/server notifications_publish` в 🎭・роли — постоянная панель подписок; повтор редактирует существующее сообщение.
- HUB → Помощь → Уведомления — самостоятельная подписка/отписка.
- `/welcometest` — проверить стандартное welcome и опубликованный template override. Тестовое приветствие — отдельное сообщение, не реальное событие вступления.

Турнирный журнал, модерация, магазин и действующие турнирные обработчики сохраняются; полный аудит их финансовых и правовых маршрутов не заменяется этой миграцией.

## Ошибки и откат

- `pending`/`uncertain` после Discord API не означает, что действие не выполнено. Проверить фактические ID и состояние. Не удалять pending-маркеры вслепую: это создаёт дубликаты.
- После ручного подтверждения, что операция выполнена, администратор в остановленном процессе сохраняет её `created_id`/`state=done`, сверяет последующие bindings и только затем возобновляет план. Если точно не выполнялась — `state` можно сбросить после сохранения резервной копии плана. Это ручное восстановление, а не автоматическая гарантия.
- `/server reconstruction action:rollback plan_id:<ID>` восстанавливает имена, категории и позиции изменённых существующих каналов. Изменённые независимо ACL не перезаписываются: откат останавливается.
- Новые каналы, категории и роли при откате **остаются**, чтобы не потерять накопленные сообщения/выданные подписки. Их последующую судьбу решает владелец. Возврат расположения — не удаление новых объектов.
- Состояния `/info` с pending проверяются по фактическим сообщениям, затем в info_store восстанавливается message_id/version. Не очищать всё хранилище.
- Анонс турнира с pending сверяется по каналу и сообщению; запись в tournament_notifications.json корректируется только после фактического подтверждения отправки/неотправки. Второго пинга автоматически не будет.
