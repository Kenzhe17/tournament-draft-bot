# Spontaneous Events 2.0 (r!z3 CLASSIC)

Спонтанные события в целевом канале: 11 типов игр, sliding-гейт
активности, 4 типа наград, durable-начисления. Реализация —
`cogs/coin_drop.py` (+ `services/event_*.py`, `storage/event_*.py`).

## Игры (11)

| Игра | Механика | Время |
|---|---|---|
| Быстрый дроп (бывш. speed) | первый валидный клик | 30с |
| Розыгрыш (raffle) | случайный уникальный участник | 60с |
| Таинственные сундуки | 5 кнопок, заранее выбранный выигрышный сундук, один выбор, победитель — случайный среди угадавших | 30с |
| Быстрый счёт | модалка, первый правильный ответ | 30с |
| Меньшинство | скрытый выбор красные/синие, обе стороны непусты, ничья → нет победителя, из меньшей стороны — случайный (фиксированный приз, включая item). Распределение голосов скрыто до конца — публично видно только суммарное число участников | 30с |
| Счастливый кубик | один RNG 1–100 на пользователя, побеждает максимум, ничья → случайный | 30с |
| Растущий куш | видимая растущая числовая награда, скрытый burn-дедлайн, первый валидный клейм забирает текущую сумму; иначе без выплаты; только числовые награды (coin/XP/REP с переменными весами), без item и без ставки участника | до 45с |
| Перепутанное слово | кураторский список русских слов, модалка, первый правильный (включая алиасы) | 30с |
| Последний клик | скрытый случайный дедлайн 15–45с, один клик на пользователя, побеждает последний принятый клик до дедлайна | 15–45с |
| Угадай число | загаданное целое 1–20, одна попытка-модалка, первый правильный | 30с |
| Крокодил | кураторская подсказка (описание слова без раскрытия), модалка, первый правильный включая алиасы | 45с |

Одна публичная карточка на событие; кнопки/модалки — persistent
(`se2:*` DynamicItem), ошибки и подтверждения — ephemeral. Исходная
карточка редактируется финальным результатом с убранными кнопками;
чужие сообщения не трогаются (edit только по `message_id` события).

Дедлайны — иммутабельные UTC-метки (`deadline_at`/`close_at` в БД),
серверные проверки по `time.time()`; таймеры не сбрасываются при
входах. Редактирование карточки троттлится (`_CARD_EDIT_MIN_INTERVAL`),
per-second edits нет. Stale-guard: действия после `end_ts` и по
завершённым событиям отклоняются; гонки разруливаются `session.lock`
+ атомарным `event_store.settle`/`finish`
(`active→settling→finished`, строго).

## Гейт активности (заменил счётчик 100 сообщений)

Скольжение-окно **5 минут** (`events.window_minutes`), проверка
только при входящем подходящем сообщении — события не спавнятся
«по таймеру». Пороги (настраиваются в Control Center, scope=both):

- `events.min_unique_users` = 3 — минимум уникальных авторов в окне;
- `events.min_messages` = 10 — минимум зачтённых сообщений в окне;
- `events.max_per_author` = 4 — максимум зачтённых сообщений от
  одного автора в окне;
- `events.min_message_interval_seconds` = 10 — минимум секунд между
  зачтёнными сообщениями одного автора;
- `events.min_active_authors_60s` = 2 — минимум 2 разных активных
  авторов с зачтёнными сообщениями за последние 60 секунд.

Что **не** считается: боты, вебхуки, системные сообщения, сообщения
не в целевом канале, команды (`!`), дубликаты нормализованного
контента (хэш в памяти), флуд сверх `max_per_author`/интервала.
Считаются обычные сообщения **и Discord replies**
(`MessageType.reply`). Запуск события — только на **новом
засчитанном** сообщении: незасчитанное (дубль/флуд) не может
спровоцировать старт, даже если окно уже «горячее».
Настройки гейта — per-key (guild/channel): пороги разных
серверов не протекают друг в друга. Тела сообщений не
персистятся — только `(author_id, ts, content_hash)` в памяти
с TTL; старые сэмплы вытесняются.

**Кулдаун**: 15 минут (`events.cooldown_minutes`) от **успешного
старта** события, персистентно (`event_channel_state` в PG,
переживает рестарт). Трекер активности продолжает работать и во время
кулдауна — окно «горячее» к моменту его окончания, но запуск
возможен только по сообщению при пройденном гейте.

**Один активный ивент на гильдию/канал**: атомарный claim
(`event_channel_state` + `spontaneous_events`), естественный спавн и
`/forcedrop` не могут создать второй; бэклога после тишины/рестарта
нет — просроченные события финализируются свипером.

## Награды (ровно 4 типа)

- **coins** — `user_balance_store.add_balance_once`, вес 50%, 100–500;
- **XP** — `player_stats_store.add_xp_once` (таблица
  `player_xp_grants`), вес 30%, 50–200;
- **REP** — `reputation_store.award_rep_logged` (source `EVENT`),
  вес 15%, 1–3;
- **item** — случайный **допустимый** предмет магазина, вес 5%.

Тип награды независим от игры (кроме «Растущего куша» — только
числовые). Приз фиксируется и персистится **до** публикации карточки
(`prize` в `spontaneous_events`); для item — конкретный `item_id`.
Если допустимых предметов нет — тип item исключается из выбора до
публикации (перевзвешивание оставшихся), молчаливой смены приза нет.

Политика допустимых предметов (`services/event_rewards.py`):
`is_active`, `item_type` cosmetic/прочее не-service и не-role,
не в `available_from/until`-окне недоступности, категория не в
`events.item_exclude_categories`. Без обхода shop-ограничений и
REP-гвардов; владение/сток проверяются при начислении
(`inventory_store.add_cosmetic` идемпотентно по ключу).

### Exactly-once и машина состояний

Событие проходит `active → settling → finished` (+`cancelled`):

1. `settle()` атомарно переводит `active→settling`:
   `SELECT ... FOR UPDATE` блокирует строку, outcome вычисляется
   из **этого же зафиксированного снимка** `actions` внутри
   транзакции (builder-callback), и только потом пишется в
   `result` — до любого начисления. Конкурирующий `patch_actions`
   либо попадает в снимок (до блокировки), либо отклоняется
   PG-гардом `state='active'`: потерянных действий и итогов «по
   устаревшему снапшоту» нет. Случайный победитель (raffle/
   сундуки/меньшинство/кубик) никогда не перевыбирается, в т.ч.
   после рестарта или при гонке двух финализаторов.
2. Обязательства по всем победителям фиксируются в
   `event_rewards` (PG) или `event_pending_rewards.json`
   (fallback). Если **ни одно** обязательство не удалось
   сохранить надёжно — событие **не закрывается**: остаётся
   `settling`, свипер повторяет.
3. `finish()` атомарен и переходы **строгие** (проверяются в
   самом UPDATE): `finished` — только из `settling` и только при
   наличии валидного `outcome` в сохранённом `result`;
   `cancelled` — только из `active`. Settling без outcome не
   закрывается никогда (критический лог, ручной разбор). Слот
   канала держится (UNIQUE-индекс `active+settling`) — новых
   событий до завершения нет.

Все типы идут через `event_reward_store` (таблица
`event_rewards`, PK `grant_key = event:{event_id}:{user_id}`):
record → claim (lease) → apply → complete. Сбой apply → fenced retry
с backoff; при недоступности PG обязательство уходит в durable
JSON-файл и сеттлится воркером. Повторный вызов с тем же
`grant_key` не начисляет дважды. Legacy `drop_coin_rewards`/
`drop_pending_rewards.json` не тронуты.

**Политика дублей item**: косметические предметы не стакаются.
Если у игрока уже есть этот `item_id` (проверка durable-файла
инвентаря, не in-memory кэша) — обязательство разрешается
**компенсацией монетами** `events.item_dup_compensation_coins`
(по умолчанию 100, настраивается в Control Center; 0 = no-op
«уже есть = исполнено»). Компенсация идёт через
`add_balance_once` с отдельным идемпотентным ключом
`<grant_key>:comp` — ровно один раз, «пустая» награда успехом
не объявляется. «Фантомный» дубль после неудачного `save()`
лечится перезагрузкой инвентаря и повторной выдачей; выдача не
считается успешной без подтверждения записи в файл. Ошибка
записи JSON → исключение → retry с backoff.

**Фиксация способа исполнения (event_item_marks)**: решение
«предмет или компенсация» и размер компенсации сохраняются в
таблице `event_item_marks` ДО побочных эффектов (INSERT
`ON CONFLICT DO NOTHING` — первый писатель выигрывает).
`event_rewards.amount` для item = замороженная сумма
компенсации, зафиксированная при `record()` — смена настройки
`events.item_dup_compensation_coins` НЕ меняет существующее
обязательство. Retry различает «предмет, принадлежавший игроку
до выплаты» (mark `comp` — файл уже содержал item_id на момент
первой попытки) и «предмет, выданный этим grant» (mark `item` —
после крэха «записан, но ledger не завершён» повтор видит
свой предмет и возвращает `owned` БЕЗ компенсации). И предмет,
и компенсация за одну награду невозможны. `event_rewards.result`
хранит фактический итог (`item`/`owned`/`comp:N`) — финальная
карточка показывает именно его; после позднего retry
`_sync_reward_card` перечитывает результат и обновляет карточку.

**PG-гарды действий** (`patch_actions`): одна UPDATE с
`state='active'`, эффективным дедлайном `LEAST(deadline_at,
close_at) > now()` по часам БД и `must_absent`-ключами
(`winner`, `choice:<uid>` для сундуков, `guess:<uid>`,
`roll:<uid>`, `click:<uid>`, `gclaim`, `p:<uid>`) —
неизменяемые действия и выбор победителя защищены на уровне
PostgreSQL, а не только в памяти. «Растущий куш» фиксирует
первый клейм глобальным ключом `gclaim = {"uid","elapsed"}`
(один must_absent на всё событие — два simultaneous клейма
разных игроков не проходят); `claim:<uid>` — legacy-формат.
«Угадай число» фиксирует попытку и победителя **одним** патчем
`{guess:<uid>, winner}` с must_absent по обоим — состояние
«попытка сожжена, победитель потерян» невозможно. Выбор в
«Меньшинстве» подтверждается только после успешного
`patch_actions`. Дедлайн перепроверяется после получения
`session.lock`.

## Конфигурация (Control Center, без деплоя)

Ключи `events.*` в `services/settings_registry.py` (scope=both,
guild может переопределять global). Мастер-флаг —
`feature.coin_drop_enabled` (legacy-ключ `coin_drop_enabled`).
`events.type_weights` — веса типов игр (JSON; равные по умолчанию,
без немедленного повтора при наличии альтернатив — `last_type`
хранится в `event_channel_state`). `events.disabled_types` —
список выключенных игр. `events.reward_weights` — веса 4 типов
наград (по умолчанию coins 50 / xp 30 / rep 15 / item 5).
Диапазоны: `events.coins_min/max`, `events.xp_min/max`,
`events.rep_min/max`; `events.growing_burn_min/max_seconds`;
`events.item_dup_compensation_coins` — компенсация монетами
при дубле предмета (см. политику дублей).

`/forcedrop` — только владелец (`BOT_OWNER_ID`), обходит гейт
активности и кулдаун, но НЕ обходит guard активного события и
feature-flag. Тестовые контролы — только явные команды.

## Хранение и миграции

Аддитивные таблицы (PG, `CREATE TABLE IF NOT EXISTS`):
`spontaneous_events`, `event_channel_state`, `event_rewards`,
`event_item_marks`, `player_xp_grants`. Откат = revert
коммита: таблицы можно не удалять (не мешают), код
возвращается к legacy coin_drop.

## Восстановление после рестарта

`cog_load` → `_restore_sessions()`: активные события из
`spontaneous_events` пересоздаются как `_EventSession`, финиш-
задачи ставятся на остаток времени, просроченные финализируются
сразу; `settling`-события доводятся через `_resume_settling`
(обязательства повторяются идемпотентно, outcome — только из
сохранённого `result`, RNG не перевыбирается). `state`/`actions`/
`deadline` — в БД, поэтому рестарт не теряет ходы и не дублирует
выплаты (grant_key + атомарный finish + settle-снапшот).

Восстановление карточки: `message_id` → fetch; при потере —
скан истории канала (до 100 сообщений) по маркеру `se2:{eid}` —
и в footer эмбеда (legacy), и в дереве Components V2
(TextDisplay/custom_id `se2:{eid}:*`). Кулдаун и `last_type`,
утерянные при крэше между публикацией карточки и `mark_started`,
восстанавливаются на `finish` из `config.cooldown_s` +
`started_ts` через `ensure_channel_state` — запись выполняется
ДО перехода в `finished`, поэтому «finished без channel_state»
невозможен (крэш → settling → идемпотентный retry свипером).
Recency-guard сравнивает `last_event_started_at` (момент старта),
а не `cooldown_until` — изменение продолжительности кулдауна
между событиями не ломает защиту от перезаписи более новым.
Refresh и финальный edit сериализованы
`session.card_lock`; неудачные финальные правки повторяет
свипер `_sweep_failed_cards` в течение 24 часов.

Синхронизация карточки с фактическими выплатами:
`_sync_reward_card` после каждого успешного `complete`
(event_rewards, в т.ч. поздний retry) ПЕРЕСЧИТЫВАЕТ
`grant_status` по живым строкам (все completed → credited;
есть pending/processing → queued; строки нет → failed) и
доливает актуальные `grant`/`rewards` в `spontaneous_events.
result` через `patch_result` (jsonb ||, только finished) —
повторные правки карточки и свипер видят свежий итог, а не
устаревший снимок на момент finish.

## Откат (rollback runbook)

Откат кода = revert коммитов ветки; таблицы `spontaneous_events`,
`event_channel_state`, `event_rewards`, `event_item_marks`,
`player_xp_grants` аддитивны и могут остаться — legacy-код их
не читает.

Безопасная последовательность при необходимости экстренного
отключения:

1. **Отключить новые запуски**: выставить
   `feature.coin_drop_enabled = false` (Control Center) —
   `on_message`-триггер и `/forcedrop` перестают стартовать
   события. In-flight события при этом НЕ прерываются.
2. **Дождаться завершения активных**: события доигрывают сами
   (finish-задачи + свиперы); либо перезапустить бота —
   `_restore_sessions` доведёт их штатно.
3. **`settling`-события**: при откате кода строки `state=
   'settling'` новому (старому) коду неизвестны — они не будут
   ни восстановлены, ни закрыты автоматически. До отката
   убедиться, что `list_settling()` пуста; если нет — сначала
   довести их текущим кодом (свипер `_sweep_settling` тикает
   каждые `_DROP_WORKER_INTERVAL`), либо разобрать вручную:
   проверить `event_rewards` по `grant_key = event:{event_id}:*`
   и при необходимости доначислить.
4. **Незакрытые обязательства**: `event_rewards` со статусом
   `pending`/`processing` и `event_pending_rewards.json`
   дожидаются worker-retry; не удалять — иначе возможны
   недоплаты. `drop_coin_rewards`/legacy-pending не затрагиваются.
5. **История и награды не удаляются**: `spontaneous_events`,
   `event_channel_state`, `event_rewards`, `event_item_marks`,
   `player_xp_grants`,
   `rep_balance_grants`, `user_balance` — append-only источники
   истины; TRUNCATE/DELETE не выполнять.

Миграция UNIQUE-индекса (`DROP INDEX IF EXISTS` +
`CREATE UNIQUE INDEX IF NOT EXISTS` по `state IN
('active','settling')`) сериализована `pg_advisory_lock` —
безопасна при нескольких процессах/инстансах.

## Семантика «последнего клика» и «куша»

- **Последний клик**: `close_at` — скрытый дедлайн (15–45с от
  старта, в `config`), `deadline_at` — публичный (45с). Победитель —
  участник с max `click:{uid}` timestamp ≤ `close_at`.
- **Растущий куш**: `burn_after` в `config` (15–40с), публичный
  дедлайн 45с. Текущая сумма линейно растёт от `prize.start` к
  `prize.amount`; клейм до burn → победа с payout=текущая сумма;
  после burn → «сгорел», выплаты нет. Никаких ставок.

## Staging-деплой (изолированный экземпляр)

Staging = отдельный процесс бота с собственными `.env`, БД и
токеном — production не затрагивается. Минимальный `.env.staging`:

```
DISCORD_TOKEN=<токен ТЕСТОВОГО бота — НЕ production>
DATABASE_URL=<URL отдельной staging-БД PostgreSQL>
GUILD_ID=<ID тестового сервера>
ALLOWED_GUILD_IDS=<ID тестового сервера>
BOT_OWNER_ID=<ID владельца для /forcedrop>
```

Запуск (из корня репо, отдельная data-директория):

```
docker compose -f docker-compose.yml --env-file .env.staging up -d --build
# или локально: python -m bot   (с env из .env.staging, DATA_DIR=./data-staging)
```

Важно: `data/` содержит JSON-инвентарь и pending-файлы — для
staging использовать ОТДЕЛЬНУЮ директорию (`./data-staging`),
иначе тестовые выдачи предметов попадут в production-инвентарь.
Миграции аддитивны и применяются автоматически при первом
обращении к стору (`CREATE TABLE/INDEX IF NOT EXISTS`).

Чеклист staging E2E: все 11 игр × 4 типа наград; живой рендер
Components V2 (карточка, кнопки, модалки); ephemeral-приватность
ответов; отсутствие спама в чат; кулдаун 15 мин; sliding-гейт
(3 юзера/10 сообщений/4 на автора/2 активных за 60с); рестарт
бота во время активного события и во время выплаты; `/forcedrop`
от владельца и отказ посторонним; ключи `events.*` в Control
Center; дубликат предмета → компенсация с суммой из
`events.item_dup_compensation_coins`.
