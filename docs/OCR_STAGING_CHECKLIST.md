# OCR Ranked Matchmaking — Staging Checklist

Инструкция по ручному тестированию OCR-конвейера Ranked Matchmaking
на отдельном Discord-сервере и изолированной PostgreSQL.

> **ВАЖНО**: все проверки выполнять ТОЛЬКО на тестовом сервере и
> тестовой БД. Production-статистика, ELO и балансы не затрагиваются.

---

## 0. Подготовка окружения

### 0.1. Переменные окружения

Обязательные для staging-инстанса:

| Переменная | Назначение | Пример staging-значения |
|---|---|---|
| `DISCORD_TOKEN` | Токен ОТДЕЛЬНОГО staging-бота | `Bot <staging-token>` (не production!) |
| `DATABASE_URL` | Изолированная тестовая PostgreSQL | `postgresql://user:pass@host:5432/rz3_staging` |
| `DATA_DIR` | Том для JSON-хранилища | `/app/data` (Railway Volume) |
| `RESULT_CHANNEL_ID` | Канал итоговых карточек | ID канала staging-сервера |
| `OCR_STATS_CHANNEL_ID` | Канал публикации OCR-скриншотов | ID канала staging-сервера |
| `BOT_OWNER_ID` | Discord ID владельца (strict admin) | ID тестового аккаунта |

Остальные переменные — как в `.env.example` production-конфига,
но со staging-значениями (каналы, роли, ID сервера).

### 0.2. Отдельная тестовая PostgreSQL

1. Создать отдельную БД/кластер (Railway Postgres сервис или локальный pgserver).
2. Применить миграции/схему — таблицы `match_finalizations`,
   `player_stats`, история матчей, экономика.
3. Заполнить ТОЛЬКО тестовыми пользователями (8+ аккаунтов или
   тестовые Discord-аккаунты на staging-сервере).
4. Проверка подключения:
   ```sql
   SELECT * FROM match_finalizations LIMIT 5;
   SELECT COUNT(*) FROM player_stats;
   ```

### 0.3. Отдельный Discord Bot Token

1. Создать второго бота в Discord Developer Portal
   (приложение-копия staging-бота).
2. Пригласить его ТОЛЬКО на тестовый сервер
   (OAuth2 → URL Generator → bot scope, сервер = staging guild ID).
3. **Защита от подключения к production**:
   - В `DISCORD_TOKEN` staging-инстанса — токен staging-бота.
   - Staging-бот НЕ должен быть добавлен на production-сервер
     (проверить список серверов бота через `!servers`/лог).
   - Railway-переменные staging-окружения НЕ должны содержать
     production `DISCORD_TOKEN`, `DATABASE_URL`, ID production-каналов.
   - Рекомендуется: отдельный Railway project/service для staging
     с собственным набором Variables.

### 0.4. Railway-настройки для staging

- Service: отдельный от production (другой сервис или environment).
- Variables: см. таблицу 0.1 — все ID должны быть staging-сервера.
- Healthcheck: `/health` или лог запуска `setup_hook`.
- Replicas: 1 (staging не нуждается в горизонтальном масштабировании;
  несколько реплик с одним JsonStore-томом недопустимы).
- Volume: примонтировать `/app/data` — JSON-хранилище должно
  переживать редеплои.

### 0.5. Проверка Volume `/app/data`

После первого запуска:

```bash
# В Railway shell или логах:
ls -la /app/data
# Ожидается: tournaments.json, *.bak, возможно *.corrupt-*
```

- Файл `tournaments.json` создаётся после первого `store.set`.
- При перезапуске данные турниров/сессий должны сохраняться
  (проверяется сценарием 12 — рестарт во время awaiting_ocr).
- Если volume не смонтирован — после рестарта все сессии теряются
  (симптом: матч «забывает» загруженный скриншот).

### 0.6. Безопасное тестирование без изменения реальных данных

- Все 8+ участников матча — тестовые Discord-аккаунты на staging-сервере.
- `DATABASE_URL` указывает ТОЛЬКО на staging-БД — перед стартом
  бота выполнить `SELECT current_database()` и убедиться в имени.
- Не использовать production-токен и production-DB ни в одной
  переменной окружения staging-инстанса.
- ELO/монеты/статистика меняются только у тестовых аккаунтов —
  это допустимо и является целью проверки.

### 0.7. Откат staging deployment

- Railway → service → Deployments → предыдущий успешный деплой →
  «Redeploy».
- Если данные повреждены: volume `/app/data` → восстановить
  `tournaments.json` из `*.bak` (см. `storage/json_atomic.py`).
- Staging-БД можно пересоздать полностью — production не затрагивается.

## 1. Сценарии функционального тестирования

### Сценарий 1. Создание Ranked-матча на 8 игроков

**Действия:**
1. На staging-сервере выполнить команду создания Ranked MM-матча
   (например `r!z3` → создание MM-очереди/матча на 8 мест).
2. Зарегистрировать 8 тестовых аккаунтов.
3. Дождаться подбора всех 8 игроков.

**Ожидаемый результат:**
- Матч создан, сформированы 2 команды.
- Команды сбалансированы по Smart Balance (ELO/статы распределены
  равномерно — проверить в карточке матча).
- У каждого игрока есть роль/доступ к каналу матча.

**Проверка:**
- Визуально: карточка матча показывает 2 команды по 4 игрока.
- PostgreSQL: `SELECT * FROM match_history` — запись о матче
  после финализации (пока пусто — матч не завершён).
- Логи бота: строки создания MM-матча без ошибок.

---

### Сценарий 2. Формирование команд по Smart Balance

**Действия:**
1. Создать несколько матчей подряд с разными аккаунтами
   (или проверить уже созданный в сценарии 1).
2. Сравнить распределение ELO/статов между командами.

**Ожидаемый результат:**
- Команды сбалансированы: суммарный MMR/ELO команд примерно равны,
  нет «стеков» сильных игроков в одной команде.

**Проверка:**
- `SELECT user_id, elo FROM player_stats ORDER BY elo DESC;`
  — сравнить суммы по командам вручную.
- Smart Balance не должен менять ELO-формулу — только
  распределение.

---

### Сценарий 3. Создание Discord-канала матча

**Действия:**
1. После формирования команд проверить список каналов сервера.

**Ожидаемый результат:**
- Создан отдельный канал вида `cs-4x4-match-N` (match_channels).
- В канале — карточка матча с кнопками («Отправить результат»,
  «Неправильный скриншот» и др.).
- Доступ к каналу — только у участников матча и организаторов.

**Проверка:**
- `tournaments.json` → `match_channels` содержит
  `"<channel_id>": {"match_type": ..., "match_index": ...}`.
- Попытка зайти в канал посторонним аккаунтом — отказ Discord.

---

### Сценарий 4. Загрузка скриншотов Rooms (1–10 комнат)

**Действия:**
1. В канале матча нажать «Отправить результат» (или использовать
   кнопку добавления скриншотов на сообщении прогресса).
2. Загрузить скриншоты комнат по одной, указывая номер комнаты
   (1..N, до 10).
3. Проверить прогресс-сообщение после каждой загрузки.

**Ожидаемый результат:**
- Каждая комната принимается только с явным номером (картинка
  в чат без номера отклоняется с подсказкой).
- Прогресс `rooms_received/rooms_expected` обновляется.
- Дубликаты/неверные номера отклоняются.
- После последней комнаты начинается OCR-маппинг.

**Проверка:**
- `tournaments.json` → `ocr_sessions[key].rooms` — массив
  комнат с данными.
- `status`: `collecting` → `awaiting_mapping`/`mapping`.

---

### Сценарий 5. Загрузка Classic и Squad

**Действия:**
1. **Classic**: капитан одной из команд отправляет один
   двухпанельный скриншот результата.
2. **Squad**: капитаны обеих команд отправляют по одному
   детальному скриншоту своего отряда (первый — с назначением
   команды, второй — аналогично; либо через squad_pool +
   кнопки выбора команды).

**Ожидаемый результат:**
- Classic: создаётся сессия `awaiting_mapping`, сообщение
  с картинкой и кнопками маппинга в stats-канале.
- Squad: `squads["0"]` и `squads["1"]` заполнены, статус
  `mapping`, два сообщения (по одному на отряд) или общий
  прогресс — по текущей реализации.

**Проверка:**
- `tournaments.json` → `ocr_sessions[key].mode` =
  отсутствие/`"squad"`, `squads`, `panels`.
- В stats-канале — сообщения с View-кнопками.

---

### Сценарий 6. Одновременная отправка двумя капитанами

**Действия:**
1. Подготовить два аккаунта-капитана (по одному в каждой команде).
2. Одновременно (в пределах ~1 сек) отправить скриншоты
   в канал матча / через кнопку.
3. Повторить несколько раз, меняя кто «первый».

**Ожидаемый результат:**
- Только ОДИН комплект принимается — от первого отправителя.
- Второй капитан получает отказ «уже загружен скриншот»
  (для squad — может загрузить свой отряд после завершения
  OCR первого, без смены победителя).
- `winning_team_index` = команда первого отправителя.
- `uploaded_by` = Discord ID первого отправителя.

**Проверка:**
- `tournaments.json` → `ocr_sessions[key].winning_team_index`,
  `.uploaded_by` — соответствуют реально первому отправителю.
- Логи: одна сессия, нет двух параллельных `awaiting_ocr`.

---

### Сценарий 7. Победитель по первому принятому файлу (не по OCR)

**Действия:**
1. Капитан команды A отправляет файл.
2. Сразу после — капитан команды B отправляет свой.
3. Если возможно, искусственно замедлить OCR первого
   (большой файл) — порядок завершения OCR не должен влиять.

**Ожидаемый результат:**
- `winning_team_index` всегда = команда A (первый принятый файл).
- Banner/сторона на скриншоте B не переопределяет победителя.
- В Ranked MM победитель определяется ТОЛЬКО по Discord ID
  отправителя первого комплекта.

**Проверка:**
- `tournaments.json` → `winning_team_index`, `winner_pending=false`.
- После финализации: ELO начислен так, будто выиграла команда A.

---

### Сценарий 8. OCR и сопоставление Discord ID

**Действия:**
1. Дождаться завершения OCR (сообщение в stats-канале с
   кнопками маппинга).
2. Игроки нажимают «Это мой ник» и выбирают свой игровой ник.
3. Для нераспознанных строк капитан назначает привязку вручную.

**Ожидаемый результат:**
- Интерфейс маппинга виден только участникам матча.
- Каждая строка скриншота привязывается к Discord ID.
- Автоматически определяется сторона (left/right) и победитель.

**Проверка:**
- `tournaments.json` → `ocr_sessions[key].maps` — заполнено
  `discord_id` для всех строк.
- `panel_picks` — выбранные панели (для classic).

---

### Сценарий 9. Исправление K/D/A/Damage

**Действия:**
1. После маппинга открыть редактирование строки (модалка
   или кнопка правки — в зависимости от режима).
2. Изменить одно из полей K/D/A/Damage на неверное значение,
   затем исправить.
3. Проверить, что изменения сохраняются и не ломают маппинг.

**Ожидаемый результат:**
- Правки применяются к `temp_stats`/сессии.
- После финализации в `player_stats` попадают ИСПРАВЛЕННЫЕ
  значения, а не исходные OCR.
- Правки после `finalizing`/`completed` блокируются.

**Проверка:**
- PostgreSQL:
  ```sql
  SELECT user_id, kills, deaths, assists, damage
  FROM player_stats WHERE match_id = '<id>';
  ```
  — значения соответствуют исправленным.

---

### Сценарий 10. Автоматическая финализация

**Действия:**
1. Завершить маппинг всех строк (последнее сопоставление).
2. Наблюдать за статусом матча и логами.

**Ожидаемый результат:**
- Финализация стартует АВТОМАТИЧЕСКИ — без нажатия
  «Подтвердить результаты» (для Ranked MM).
- Статус сессии: `awaiting_mapping`/`mapping` → `finalizing`
  → `completed`.
- Начисляется ELO каждому игроку (8 записей).
- Обновляется статистика (kills/deaths/assists/damage).
- Публикуется итоговая карточка в `RESULT_CHANNEL_ID`.
- Карточка матча в канале → состояние «завершён».

**Проверка:**
- `tournaments.json` → `ocr_sessions[key].status == "completed"`,
  `.result_message_id` заполнен.
- PostgreSQL:
  ```sql
  SELECT * FROM match_finalizations WHERE match_id = '<id>';
  -- ожидается status='done'
  SELECT user_id, elo FROM player_stats WHERE match_id='<id>';
  -- 8 строк, ELO изменился ровно один раз
  ```
- Логи: `finalize_ocr_match` → `done`, без ошибок.

---

### Сценарий 11. Однократное начисление ELO

**Действия:**
1. После финализации (сценарий 10) повторить попытки:
   - нажать старые кнопки маппинга (если видны);
   - вызвать повторную финализацию через админ-команду/лог;
   - перезапустить бота и проверить recovery.
2. Проверить ELO до/после каждого действия.

**Ожидаемый результат:**
- ELO НЕ начисляется повторно — `match_finalizations.status='done'`
  блокирует повторное применение.
- Старые кнопки/взаимодействия не меняют завершённый матч.
- `processed_elo_matches` содержит match_id — повторный
  `process_match_result` пропускается.

**Проверка:**
- PostgreSQL:
  ```sql
  SELECT COUNT(*) FROM match_finalizations WHERE match_id='<id>';
  -- = 1
  SELECT user_id, elo FROM player_stats WHERE match_id='<id>';
  -- ELO значения не изменились после повторных попыток
  ```
- Сравнить `elo` в `player_stats` до и после повторного запуска —
  дельта = 0.

### Сценарий 12. Кнопка «Неправильный скриншот»

**Действия:**
1. Загрузить комплект скриншотов (любой режим).
2. До завершения маппинга нажать «Неправильный скриншот»
   от имени администратора (Discord admin).
3. Проверить состояние сессии и карточки.

**Ожидаемый результат:**
- Весь комплект отменяется: `status='cancelled'`, сессия удалена.
- `gen` инкрементирован — старые callbacks не действуют.
- Карточка матча возвращается в `active`.
- Кнопка «Отправить результат» снова доступна.
- Аудит-лог отмены.
- Повторное нажатие → «уже отменён»/no-op.

**Проверка:**
- `tournaments.json` → `ocr_sessions` не содержит ключа матча.
- Попытка не-админом нажать кнопку → отказ (ephemeral).
- Старые кнопки маппинга → ошибка «сессия не найдена».

### Сценарий 13. Повторная загрузка после отмены

**Действия:**
1. После сценария 12 капитан команды-победителя отправляет
   ПРАВИЛЬНЫЙ комплект.
2. Пройти маппинг → финализация.

**Ожидаемый результат:**
- Новый комплект принимается — кнопка загрузки восстановлена.
- `winning_team_index` = команда отправителя нового комплекта
  (может отличаться от отменённого).
- Старые callbacks нового комплекта не затрагивают.
- Матч финализируется, ELO один раз.

**Проверка:**
- `tournaments.json` → новая сессия с новым `session_id`/`gen`.
- PostgreSQL → `match_finalizations` — одна запись `done`.

---

### Сценарий 14. Перезапуск во время `awaiting_ocr`

**Действия:**
1. Капитан отправляет первый файл → сессия `awaiting_ocr`.
2. Пока OCR «висит» — перезапустить бота (Railway restart
   или kill процесса).
3. После рестарта проверить состояние сессии.
4. Владелец клейма повторно отправляет файл.
5. Попытаться отправить файл от чужого капитана.

**Ожидаемый результат:**
- Сессия `awaiting_ocr` СОХРАНЯЕТСЯ в `tournaments.json`.
- Матч НЕ заблокирован навсегда — владелец может дослать файл.
- `winning_team_index` НЕ меняется (зафиксирован при клейме).
- Чужой капитан — отказ.
- Админ-отмена работает.
- Старые OCR-задачи (мертвые после рестарта) не пишут состояние.

**Проверка:**
- `tournaments.json` → `ocr_sessions[key].status='awaiting_ocr'`
  до и после рестарта.
- После повторной отправки владельцем → `awaiting_mapping`/`mapping`,
  `winning_team_index` тот же.
- Логи рестарта: нет ошибок recovery для `awaiting_ocr`
  (recovery обрабатывает только `finalizing`).

---

### Сценарий 15. Перезапуск во время `finalizing`

**Действия:**
1. Запустить финализацию (завершить маппинг).
2. Во время `status='finalizing'` (между началом ELO и
   завершением) перезапустить бота.
3. Проверить логи и состояние после рестарта.

**Ожидаемый результат:**
- При рестарте `bot.py` → `_recover_finalizing_sessions` →
  `recover_stuck_finalizing` находит сессию.
- Финализация доводится до конца БЕЗ повторного ELO
  (PG-гейт `match_finalizations`).
- Итоговая карточка публикуется или переиспользует
  `result_message_id` (без дублей).
- `status='completed'`.

**Проверка:**
- Логи: `Recovered finalizing OCR session` или аналог.
- PostgreSQL:
  ```sql
  SELECT status FROM match_finalizations WHERE match_id='<id>';
  -- 'stats_done' → 'done' (не дублируется)
  ```
- ELO не меняется повторно (см. сценарий 11).

### Сценарий 16. Восстановление Discord Views

**Действия:**
1. Создать сессию, пройти часть маппинга.
2. Перезапустить бота.
3. Проверить: могут ли игроки продолжить сопоставление
   (старые кнопки/сообщения).
4. Проверить: может ли админ отменить.

**Ожидаемый результат:**
- Сессия и прогресс маппинга сохраняются (`tournaments.json`).
- Кнопки маппинга продолжают работать (view привязан к
  `guild_id`/`channel_id`/`match_type`/`match_index` —
  восстанавливаются при `build_view_for_tournament`).
- Админ-отмена работает.
- Завершённая сессия не предлагает повторную отправку.

**Проверка:**
- `tournaments.json` → `ocr_sessions[key].maps` — прогресс
  сохранён после рестарта.
- Нажатие кнопки после рестарта → корректное продолжение
  (нет «сессия не найдена»).

### Сценарий 17. Обработка ошибок Discord API

**Действия:**
1. Имитация сбоев (по возможности):
   - временно заблокировать/удалить stats-канал;
   - ограничить права бота;
   - запустить при нестабильной сети.
2. Попытаться загрузить скриншот / завершить маппинг.

**Ожидаемый результат:**
- Ошибки Discord API логируются (`logger.warning/exception`).
- `_room_lock` НЕ удерживается во время Discord-вызовов —
  финализация/отмена не блокируются.
- При ошибке публикации `message_id` не записывается (или
  записывается только валидный).
- Устаревшие сообщения (отменённый комплект) гасятся —
  кнопки неактивны.
- Сессия не переходит в неконсистентное состояние.

**Проверка:**
- Логи: `OCR upload processing failed`, `Neutralize stale
  OCR message`, `Match card processing update failed` —
  без traceback'ов, блокирующих выполнение.
- `tournaments.json` → сессия в корректном статусе.

## 3. PostgreSQL — контрольные запросы

```sql
-- Все OCR-сессии и их статусы
SELECT match_id, status, winning_team_index, uploaded_by
FROM ocr_sessions_log;  -- если есть аудит-таблица
-- иначе: tournaments.json → ocr_sessions

-- Финализации матчей
SELECT match_id, status, created_at, updated_at
FROM match_finalizations
ORDER BY created_at DESC;

-- ELO-изменения по игрокам за матч
SELECT user_id, elo, kills, deaths, assists, damage
FROM player_stats
WHERE match_id = '<match_id>';

-- История завершённых матчей
SELECT * FROM match_history
WHERE match_id = '<match_id>';

-- Экономика (если применимо)
SELECT user_id, balance FROM user_balances
WHERE user_id IN (<test_user_ids>);
```

## 4. Откат и очистка staging

1. Railway → зафиксировать последний рабочий деплой.
2. При проблемах: Redeploy предыдущей версии.
3. JSON-хранилище: при повреждении восстановить из
   `/app/data/tournaments.json.bak`.
4. Staging-БД: можно очистить `TRUNCATE` тестовых таблиц
   или пересоздать БД — production не затрагивается.
5. Staging-бот: отключить/удалить с тестового сервера после
   завершения проверки.
