# CASH CUP — интеграция в r!z3 CLASSIC

Рабочая ветка: `feat/cashcup-rc`, целевая: `feat/classic-riz3-cv2`.
Функция выключена по умолчанию: `CASHCUP_ENABLED=0`. Включение — только после отдельного разрешения.

Независимый Double Elimination с **любым количеством команд от двух**. Победа в матчах Winners/Losers — BO1. Единственный Grand Final — BO3, до **двух побед**; **reset отсутствует**. Команды: 4 основных игрока + максимум один запасной; максимум два ПК/эмулятора на заявку, включая запасного. Глобальный лимит BR-команды в 4 игрока не меняется.

## Архитектура

- Система — часть cog `cogs/cashcup.py` + `services/cashcup_store.py` (PostgreSQL JSONB, атомарные `mutate` с `FOR UPDATE`, аудит `cashcup_audit`) + `services/cashcup_bracket.py` (движок сетки).
- В дереве Discord только две команды: `/cashcup create` и `/cashcup panel` (обе ADMIN).
- Все остальные действия — persistent кнопки, Select Menu и Modal на публичной карточке и Match Board. Обработчики восстанавливаются после перезапуска из актуального состояния PostgreSQL.
- Регистрация: капитан собирает команду через `/team` (BR), затем нажимает «Зарегистрировать команду». Создаётся независимый снапшот CASH CUP; изменения `/team` после этого не влияют на заявку.
- Каждый игрок сам подтверждает свой Free Fire UID, регион и устройство через Modal («Мои данные») — UID привязывается к Discord-аккаунту игрока, чужой аккаунт подтвердить нельзя.
- ADMIN вручную проверяет владение UID и членство/тег/VAC; `verified=True` выставляется только после полной проверки профиля. Изменение UID/профиля сбрасывает `verified`.
- Максимум 2 устройства `pc` на команду; уникальность Discord ID и Free Fire UID по всему турниру; ровно 4 основных игрока; перед стартом проверяются `ff_ok`, `verified`, ник, регион, формат UID, тег r!z3 и отсутствие активного VAC — иначе старт отклоняется без создания сетки.
- Приз: единственная сумма за 1 место + валюта (`KZT`/`USD`/…). 2-е и 3-е места всегда 0. Приз задаётся и меняется только в статусе `registration`; перед стартом и внутри транзакции `mutate` проверяется положительная сумма, валюта и неизменность `prizes` относительно проверенного снимка. Турнир без приза не запускается.
- Match Board — одно публичное сообщение на турнир (`board_message_id`), пагинация по 15 матчей, единый срез для Embed и Select. При перезапуске доска восстанавливается после готовности Gateway (`on_ready`), обновляется на месте; замена создаётся только при `discord.NotFound`, при 403/429/5xx дубликаты не создаются.
- Результаты: обычный матч требует check-in обоих капитанов и выданную комнату; BO1 принимает только `1:0`/`0:1`, сторона — строго `a`/`b`. Спорные матчи (`DISPUTED`) блокируют продвижение раунда до решения ADMIN; revert, DQ, forfeit и BYE работают через тот же движок. GF — только через кнопки выбора победителя игры с реальным счётом серии.
- Пароли комнат не публикуются: данные комнаты видны только участникам матча и уполномоченным ADMIN.

## Хранение и безопасность

Две таблицы PostgreSQL создаются при первом обращении: `cashcup_tournaments` (JSONB, атомарные обновления с блокировкой записи) и `cashcup_audit` (события). Старые схемы, экономики, турниры, BR, MM, Ultimatum, SHOP 2.0, VAC и модерация не меняются. После перезапуска регистрации, сетки, результаты и комнаты восстанавливаются из PostgreSQL.

Принцип Double Elimination: вторая неудача в нижней сетке исключает команду. В Grand Final — одна серия BO3 без bracket reset и без преимуществ победителю Winners Bracket.

**Реальные деньги:** приз перечисляет организатор вручную вне бота. ADMIN фиксирует факт через «Отметить выплату»: получатель обязан быть игроком команды-чемпиона, сумма строго равна призу за 1 место, валюта совпадает, повторная отметка запрещена. Все проверки — внутри транзакции PostgreSQL. Бот **не выполняет денежных переводов** и не начисляет монеты/балансы. В аудит пишутся: ID турнира, чемпион, получатель, сумма, валюта, место, ADMIN, время, подтверждение, `manual=True`. Пароли комнат и токены в журнал не пишутся.

**Ограничения, требующие человеческой проверки:** Free Fire API сообщает игровой ник по UID, но не доказывает владение аккаунтом; тип устройства заявляет пользователь, API не является достоверным детектором ПК/эмулятора. Организатор должен проверять спорные аккаунты и устройства. Проверка членства/тега зависит от актуальных полей Discord API и требует проверки на живом сервере.

**One-day условие:** при произвольном числе команд завершение за один день не гарантировано. `/cashcup forecast` не является обещанием; организатор должен выделить комнаты и волонтёров до закрытия регистрации.

**Реальные деньги (правовое):** перед запуском проверьте региональные правовые требования, правила Garena и публично опишите срок, способ и критерии выплаты, порядок апелляций и допуск несовершеннолетних. Не смешивайте денежные призы с монетами, ставками или балансами бота.

## Порядок безопасного включения (после разрешения)

1. Убедиться, что PostgreSQL доступна, заданы `CASHCUP_ENABLED=1` и `FREEFIRE_API_KEY`.
2. Запустить бота, дождаться `on_ready`, проверить восстановление досок.
3. Создать тестовый турнир на малом числе команд, пройти сценарий до конца.
4. Проверить выплату, аудит и отсутствие побочных эффектов на BR/SHOP/экономику.

## Пример полного сценария

1. ADMIN: `/cashcup create prize:"100000 ₸ чемпиону" amount:100000 currency:KZT`.
2. Капитан собирает команду из 4 игроков через `/team`, затем нажимает **«Зарегистрировать команду»** на карточке CASH CUP.
3. Каждый игрок нажимает **«Мои данные»** и сам вводит Free Fire UID/регион/устройство. При необходимости капитан приглашает запасного — пятый игрок подтверждает данные по приглашению.
4. ADMIN сверяет аккаунты и устройства, затем в **«Управление» → «Проверить команду»** подтверждает UID; при необходимости удаляет команду или назначает приз.
5. **«Управление» → «Запустить турнир»** — проверка всех заявок, состава, FF-профилей, тега, членства, VAC, уникальности, приза и генерация сетки.
6. На публичной доске матчей капитаны открывают свой матч и подтверждают готовность; ADMIN выдаёт комнату и подтверждает результаты через карточку матча или меню.
7. В `GF` ADMIN записывает каждую игру через **«Игра GF»**. Счёт 2:0 или 2:1 завершает CASH CUP.
8. Приз перечисляется вручную вне бота; ADMIN фиксирует факт через **«Отметить выплату»** — только игроку команды-чемпиона, сумма и валюта должны совпадать с призом, повторная отметка запрещена.
9. Обычное подтверждение результата требует: оба check-in, выданную комнату и ссылку-доказательство. Исключения — только через «Тех. победа» или решение спора.

## Staging E2E и разделение хранилищ (важно)

- Публичные публикации (`cogs/cashcup_public.py`) читают **только**
  `cashcup_tournaments` через `cashcup_store.latest(guild_id)` —
  «источник истины» для сетки и карточек.
- Тестовая команда `/тест` (только при `CASHCUP_TEST_ENABLED=1`,
  staging) работает с **отдельной** таблицей `cashcup_test_sessions`
  и никогда не трогает `cashcup_tournaments`.
- Следствие: E2E публичных карточек нельзя проводить на `/тест`-сессии.
  Нужен **обычный** Cash Cup турнир, созданный командами `/cashcup`
  на staging-сервере (staging-БД изолирована от production, поэтому
  это безопасно). `/тест` — только для симуляции/деградации.
- Публичные каналы задаются `CASHCUP_BRACKET_CHANNEL_ID` и
  `CASHCUP_MATCH_CHANNEL_ID`. Значение `0` (по умолчанию) выключает
  публикации — production можно релизить с выключенными флагами.
- Пароли комнат в публичные сообщения не выводятся.
